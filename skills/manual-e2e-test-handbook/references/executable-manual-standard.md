# 可执行人工测试手册标准

本标准用于把机测记录转换成操作者可以从干净本地环境逐步复制执行的 runbook。测试结果表不能替代操作步骤；“已验证”也不能替代命令、输入、预期输出和失败处理。

## 最终手册门禁

只有同时满足以下条件，手册才能标记为 `machine-validated` 和 `可执行`：

- 目标操作系统、Shell、仓库目录、Compose 文件、服务名、端口和依赖已固定。
- 所有变量在“环境变量与路径”中定义，并有赋值命令、来源或明确的人员输入格式。
- 启动、健康检查、数据构造、触发、结果核验、清理和清理复查都有逐条命令或明确 UI 操作。
- 每个新功能和回归 Case 都有独立的步骤表：顺序、工作目录、命令/动作、预期结果、实际结果、通过标准和证据。
- 数据库和 Redis 操作使用 Docker 容器内客户端；不能要求操作者在主机安装或调用客户端。
- 每条命令符合目标 Shell，Windows 命令使用 `cmd.exe`，单条命令控制在约 100 个字符以内；超长操作必须拆成多个步骤。
- 每个命令都是本轮实际成功执行过的命令，或明确标记为 `Blocked/待人员输入`；禁止从源码或记忆补写为“可执行”。
- 每个失败分支都给出下一条诊断命令、停止条件和重新执行的 Case；不能只写“检查日志”或“重试”。

不满足任一项时，输出 `可执行性不完整`，列出缺失项和补测动作，不得把叙述性草稿当作最终手册。

## 手册固定结构

### 1. 环境与变量初始化

先给出一组可复制的 `cmd` 步骤：进入仓库、设置短路径、设置测试前缀、端口、容器名和凭据变量。每个值都要说明来源；秘密只能写变量名，不能写真实值。

示例形状：

```cmd
cd /d C:\path\to\repo
set TD=%USERPROFILE%\.codex\skills\manual-e2e-test-handbook\workspace
set TEST_PREFIX=E2E-<run-id>
set APP_PORT=18082
```

如果必须由操作者填写，紧邻给出格式和验证命令，例如 `set DEVICE_ID=TEST-123`、`echo %DEVICE_ID%`；不能只留下 `<DEVICE_ID>`。

### 2. 前置检查和启动

每个服务必须有明确的启动命令、健康检查命令和通过输出。需要 fixture、responder 或消息订阅者时，必须给出实际启动命令、监听端口、输入 payload 和停止命令。不要使用“启动服务”“准备 responder”“确认依赖正常”这类无命令步骤。

### 3. 数据和消息构造

每条数据库写入都给出完整的 Docker 命令、表名、字段和值来源；每条 Redis 写入都给出完整的 Docker 命令、key、value、TTL 和验证命令。MQTT、HTTP、文件或定时触发也必须给出具体命令、payload 文件内容或逐项 UI 操作。

### 4. Case 步骤表

每个 Case 使用以下字段，不合并成一段叙述：

| 步骤 | 工作目录 | 命令/动作 | 预期输出或状态 | 实际结果 | 通过标准 | 证据 |
|---|---|---|---|---|---|---|
| 1 | `<cwd>` | `<one cmd or exact UI action>` | `<exit code/response/log>` | `<observed>` | `<pass rule>` | `<path>` |

一条命令一个代码块；命令依赖前一步变量时标明依赖。每个 Case 末尾必须有“失败时执行”小节，包含一条诊断命令和停止/升级条件。

### 5. 结果核验和清理

响应、日志、数据库、Redis、消息、对象存储和下游读回都要有可复制的查询命令。清理必须按创建顺序的反向顺序执行，包含数据、key、对象、临时文件、fixture 和本轮启动的服务，并在最后给出复查命令。

## 命令记录要求

- 机测时实时保存成功命令和关键输出，生成手册时从命令记录复制，不从最终结果反推。
- 对同一变量只定义一次；命令中优先使用短变量，避免超长路径和不可见默认值。
- `<PLACEHOLDER>` 只能表示操作者必须提供的值，并且必须在前面的变量表中有格式、来源和验证步骤。
- “观察日志”“查看数据库”“检查 Redis”“确认上传成功”都不是命令；必须替换为具体的 `docker logs`、`docker exec`、`curl`、`dir` 或项目已有脚本命令。
- 命令执行失败时保留原命令、退出码、关键输出和容器状态；后续步骤必须明确是停止、诊断、修复后重测还是继续。

## 发布前自检

逐项检查并在手册中记录结果：

```text
[ ] 从环境初始化开始可以按顺序执行，不依赖聊天上下文
[ ] 每个变量都有定义、来源和格式
[ ] 每个服务都有启动、健康检查和停止命令
[ ] 每个 Case 都有命令/动作、预期、实际、通过标准和证据
[ ] 数据库/Redis 命令都通过 Docker 容器执行
[ ] 没有“准备/观察/模拟/检查”但没有具体动作的步骤
[ ] 没有未定义占位符或未经执行的伪命令
[ ] 所有命令符合目标 Shell 且长度受控
[ ] 失败分支和清理复查可以独立执行
```
