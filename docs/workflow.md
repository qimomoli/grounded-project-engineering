# 协同工作流

## 0. 轻量级介入原则

这套 Skill 的目标是提供轻量级指导，而不是改变 AI 的基本工作方式或强制套用完整流程。在支持隐式调用的宿主中，Skill 由宿主根据任务相关性按需自动触发，各自只处理明确的问题边界；没有匹配场景时不应强行加载。共享规则只保留对准确性、安全性和可验证交付有实际帮助的部分，尽量减少无关上下文、重复说明和流程噪音。

## 1. 需求与 AI 价值

当任务涉及 AI 功能、Agent、MCP、自动化或“智能化”描述时，先用 `ai-necessity-audit` 将复合需求拆成可判断的能力单元，明确最小可观察结果、非 AI 基线和不可替代的 AI 增量。

没有 AI 价值判断需求时，不要为了形式强行触发该 Skill。

## 2. 证据与项目上下文

`evidence-discipline` 是全流程的证据层，要求把当前代码、运行结果、操作人员输入、推断和未知项分开。

`grounding-project-knowledge` 负责定位项目根目录、项目规则、代码路径、依赖和数据流。它维护的是当前证据的索引，不是可以替代重新阅读代码的事实缓存。

## 3. 历史坑位

`avoiding-project-pitfalls` 只能把历史记录转成检查清单和假设。必须在当前代码、配置、调用链或运行结果中重新确认前置条件后，才能影响设计、诊断、实现或评审。

不能因为另一个项目出现过相同症状，就直接复制根因或修复方案。

## 4. 变更授权

任何写文件、改 Git 状态、启动或重启服务、写测试数据、修改数据库/缓存、发送消息、创建 PR 或推送代码之前，使用 `confirm-before-work` 明确：

- 动作和目标；
- 精确文件、目录、服务或资源范围；
- 预期变更；
- 间接副作用；
- 假设、边界和未决问题。

批准范围发生变化时必须重新确认。

## 5. 本地 E2E

当变更需要 Docker-backed 验证或人工测试手册时，使用 `manual-e2e-test-handbook`：

1. 先建立变更范围清单；
2. 先做每个应用的隔离验证；
3. 隔离验证通过后再做多应用链路；
4. 记录新行为、受影响旧行为、未知影响和排除项；
5. 从真实执行结果生成手册；
6. 不把跳过、部分观察或源码推断标记为通过。

该 Skill 默认只允许本地资源，不允许把运行状态、项目知识、日志、视频和业务数据提交到本仓库。

命令生成按目标操作系统分支：Windows 保持 `cmd.exe`；Linux/macOS 使用 POSIX shell。默认使用本次执行环境，若目标系统不同，必须显式记录并确认 override。

## 6. 安装策略

建议把整个仓库作为一个版本化套件获取，再将六个 Skill 目录整体安装到目标 Agent 的 Skill 根目录。单独下载某一个 Skill 可能丢失：

- 配套的 schema 和维护脚本；
- 统一的证据和授权边界；
- E2E 的运行状态与手册模板；
- Skill 之间的触发顺序和适用边界。

## 7. 仓库文档分工

- `README.md` 面向首次浏览仓库的人，提供定位、快速入口和公开边界。
- `docs/installation.md` 面向安装和升级套件的人，说明目录映射和运行时资料边界。
- 本文件面向需要理解协同方式的人，说明触发条件、顺序和职责边界。
- `LICENSE` 说明代码、Skill 文本和文档的再使用授权。

这些文档描述的是通用 Skill 套件，不记录任何具体业务项目、个人环境或运行结果。

## 8. 仓库验证入口

仓库级结构检查和测试编排统一通过 `python -m gpe validate` 与 `python -m gpe test` 执行；GitHub Actions 在 Windows 与 POSIX runner 上重复执行这些入口。
